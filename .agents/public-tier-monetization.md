### 3.1b ผู้บริจาคกดรับแต้มของตัวเอง — **อนุญาต ไม่ใช่การรั่วไหล** (มติ user 2026-07-24)

ให้ `R` = อัตราหักแต้มตอนบริจาค · `A` = ยอดบริจาค (บาท)

```
จ่ายไป = A × R   |   สร้างได้ = A × 1,080   |   กดคืนเองได้ = A × 1,080 × (220/270) = A × 880
กำไรสุทธิ = A × 880 − A × R
```

| R | ผลลัพธ์ |
|---|---|
| 100 (ของเสียที่ต้องแก้) | **+780A** — ปั๊มแต้มได้ |
| **1,080 (มาตรฐาน)** | **−200A** — ขาดทุนเสมอ |

**ที่อัตราถูกต้อง วงจรนี้ทำกำไรไม่ได้เลย** ขาดทุน 200 pp ต่อ 1,080 pp ที่บริจาค = 80 pp ของแพลตฟอร์ม + 120 pp ของผู้แนะนำพอดี
เหตุผลเชิงหนี้: แต้มที่ผู้บริจาคควักออกมาเป็นหนี้ของแพลตฟอร์มอยู่ก่อนแล้ว การย้าย กระเป๋าผู้บริจาค → กองกลาง → กลับมาหาผู้บริจาค **ไม่เพิ่มหนี้รวม** (ลดลงด้วยซ้ำ)
→ **ไม่ต้องใส่ guard ห้ามกดรับแต้มของตัวเอง** และไม่ต้องแตะ 212 แถวเดิมที่เกิดขึ้นแล้ว

### 3.2 ขาโฆษณา (โมเดล D1, config ปัจจุบัน)

ต่อการดู 1 ครั้ง ยาว `d` วินาที:

| รายการ | สูตร | d = 5 วิ |
|---|---|---|
| ผู้ลงโฆษณาจ่าย | `d × 0.10 ฿` | +0.50 ฿ |
| ผู้ชมจ่ายแต้ม (หนี้ลด) | `d × 20 pp` = `d × 0.0167 ฿` | −100 pp (+0.083 ฿) |
| ผู้ชมได้เงิน | `d × 0.06 + (d×20)/1200` | −0.383 ฿ |
| ผู้แนะนำได้เงิน | `d × 0.02` | −0.10 ฿ |
| **แพลตฟอร์มเหลือ** | `d × 0.02 ฿` | **+0.10 ฿ = 20%** |

**อ่านสูตรให้ถูก:** ส่วน `pp/1200` ที่คืนให้ผู้ชมคือการคืนแต้มที่จ่ายไปเป๊ะ ๆ → การดูโฆษณาคือ **ช่องทางแปลงแต้มเป็นเงิน โดยมีโบนัส 0.06 บาท/วินาที** ไม่ใช่การ "เก็บเงินค่าดู"

> หมายเหตุ: ที่ราคาเก่า 0.05 บาท/view-วินาที สมการพลิกเป็น **ขาดทุน ~0.15 บาท/การดู 5 วินาที** — สอดคล้องกับที่รับบริจาค 7,540 บาท แต่ wallet เหลือ 4,586 บาท

## 5. เส้นทางจริง 4 เส้น (ตรวจสอบแล้วโดย Codex)

### 5.1 ผู้บริจาค
`ui/pages/Earn/donates/create.vue` (**ไม่มี auth middleware**) → `POST /api/supports/donates` (public, `routes/earn/donate.php:64-65`)
→ `DonateController::store` → เก็บสลิปลง **public disk** (`:151-155`) → `remaining_points = amounts × 1080` (`:174`)
→ แตก 3 ทาง: `slip` = pending · `wallet` = หัก wallet + อนุมัติทันที · `points` = หัก `amounts × 100` pp + อนุมัติทันที
→ แสดงผลที่ `GET /api/donates/available` (**public, ไม่ต้อง login**) ซึ่งคืน **status 0 และ 1 ปนกัน** พร้อม `slip` + `donor_email`

### 5.2 ผู้ลงโฆษณา
**เส้นใหม่:** `ui/pages/Earn/Advertise/create.vue` (มี `middleware: 'auth'`) → `POST /api/campaigns` → `StoreCampaignRequest` ตรวจราคา `views × duration × 0.10` ฝั่ง server → `payment_status` unpaid/pending_slip, `review_status` pending
**เส้น legacy:** `POST /api/advertises` → `AdvertController::store` (hardcode 0.10 ที่ `:130`) → wallet = อนุมัติเอง, slip = pending

### 5.3 ผู้ดู / ผู้กดรับ
**กดรับแต้มบริจาค:** `GET /api/donates/{id}/get-donate` (ต้อง auth) → ตรวจ `status = 1` และ `remaining_points ≥ 270` → นับการกดรับวันนี้ → attach + `decrement 270` + `+240 pp` + suggester `+30 pp` — **ไม่มี transaction ไม่มี lock**
**ดูโฆษณา (ที่ใช้จริง):** `CampaignWidget.vue` → `GET /api/campaigns/widget` → `POST /api/campaigns/{id}/impression` → นับถอยหลังฝั่ง client (`:115-129`) → `POST /api/campaigns/{id}/view`
**ดูโฆษณา (pipeline ที่แข็งแรง แต่ไม่เคยถูกใช้):** `start` → `heartbeat` → `complete` พร้อม token/visibility/replay guard

### 5.4 แอดมิน
- บริจาค: `routes/earn/donate.php:71-80` — list/show/update/delete/bulk-review/receive/reject (`receive`/`reject` บังคับ status = 0 ✅)
- แคมเปญ: `PATCH /campaigns/{id}/review` — state machine ครบ ✅ + `PATCH /campaigns/{id}/payment` (ตั้ง refunded ได้)
- legacy: `PATCH /plearnd-admin/advertises/{id}/approve` — **ตั้งแค่ `status = 1` ข้าม state machine ทั้งชุด**

## 8a. กระบวนการตรวจสลิปของแอดมิน (มติ user 2026-07-24) — ช่องว่างเทียบโค้ดจริง

**เจตนาที่ user กำหนด:** แอดมินเทียบตัวเลข 3 ทาง (สลิป ↔ ยอดเข้าบัญชีจริง ↔ ยอดที่ผู้ใช้แจ้ง) → ถ้าตรง = อนุมัติ · ถ้าไม่ตรง = ปฏิเสธ **หรือระงับชั่วคราวเพื่อตรวจสอบ** แล้วแจ้งผู้ใช้ · **นโยบายไม่คืนเงินเด็ดขาด** กรณีโอนผิด/แจ้งผิด เพื่อกันการใช้ระบบเป็นทางผ่านทางการเงิน

### ✅ ที่โค้ดทำถูกอยู่แล้ว
- **นโยบายไม่คืนเงินสำหรับสลิป ทำงานถูกโดยบังเอิญอยู่แล้ว** — `CampaignRefundService::refundWallet` คืนเงินเฉพาะเมื่อ `payment_status = PAID` ส่วนแคมเปญที่จ่ายด้วยสลิปและถูก reject ยังเป็น `PENDING_SLIP` จึงไม่คืน (`CampaignRefundService.php:18-20`)
- **แคมเปญที่จ่ายด้วย wallet ถูก reject → คืนเข้า wallet** ซึ่ง**ถูกต้องและควรคงไว้** เพราะเป็นเงินภายในระบบ ไม่มีการเคลื่อนผ่านธนาคาร จึงไม่มีความเสี่ยงฟอกเงิน

### นโยบายเงินโอนผิด/แจ้งผิด — **มติ D9: เก็บเป็นเครดิต wallet**
เงินที่โอน/แจ้งผิด **ไม่โอนคืนธนาคาร** แต่**เข้าเป็นเครดิตใน wallet ของผู้ใช้** — ใช้ต่อในระบบได้ แต่จะถอนออกธนาคารต้องผ่านด่าน KYC เดิม (`BankAccountNameMatcher` บังคับชื่อบัญชีปลายทางตรงกับผู้ใช้ + maker-checker ยอดสูง)
เหตุผล: กันฟอกเงินได้เท่ากับการริบ (เงินยังติดในระบบ ออกยาก) แต่ไม่เป็นการยึดทรัพย์ผู้ใช้สุจริตที่โอนเกินโดยพลาด — ลดความเสี่ยงข้อพิพาทกฎหมายผู้บริโภค
**ต้องมี:** (ก) ข้อความ consent ให้กดยอมรับก่อนส่งรายการ · (ข) เมื่อแอดมิน reject/ปรับยอด → สร้าง `WalletTransaction` ประเภทเครดิตพร้อม audit ว่ามาจากรายการไหน · (ค) ต้องผูกกับ user จริง (guest ที่ไม่มีบัญชี → ต้องมี flow แยก เพราะไม่มี wallet ให้เครดิต — ดู §8b)

### ลิงก์ติดตาม (D8)
- คอลัมน์ `tracking_token` บน `adverts` — สุ่มยาว (≥32 ไบต์) + unique index · URL รูปแบบ `/advertise/track/{token}`
- หน้าติดตามแสดง: สถานะรีวิว · เหตุผลปฏิเสธ · ยอดที่แจ้งโอน · โควตาคงเหลือ · จำนวน impression
- **ห้ามแสดง:** สลิป · อีเมล · เบอร์โทร · ข้อมูลผู้ใช้อื่นใด (บทเรียนจาก P0 #5)
- **flow ขอลิงก์ใหม่:** guest กรอกอีเมลหรือเบอร์ที่ใช้ตอนลง + วันที่โอน → ระบบส่งลิงก์ให้ทางช่องทางนั้น
  - ถ้ามีแต่เบอร์และยังไม่มีระบบ SMS → ให้แอดมินออกลิงก์ให้จากหน้าจัดการ
  - ต้องตอบข้อความเดียวกันเสมอไม่ว่าจะเจอหรือไม่เจอ (กัน enumeration) + rate limit ต่อ IP
- token ต้องเก็บแบบ **plaintext** (ไม่ hash) เพราะต้องส่งซ้ำได้ → ชดเชยด้วยความยาวและ rate limit

### สิ่งที่ยังต้องตัดสินตอนลงมือ
- Cloudflare Turnstile + honeypot + IP rate-limit บนฟอร์ม guest (ตัดสินไว้แล้วรอบก่อน)
- `beneficiary_id` ต้องถูก **ล็อคฝั่ง backend** ห้าม guest ส่งมาเอง (ตัดสินไว้แล้วรอบก่อน)
- `CampaignRefundService` กรณี guest ถูก reject — คืนเงินยังไงในเมื่อไม่มี wallet

### ข้อมูลจริงประกอบ D2.3/D2.4 (ตรวจแล้ว)
- ผู้ใช้ 3,312 คน — **ทุกคนมี `suggester_code`** (ไม่มี null เลย) และ **3,299 คน (99.6%) resolve เป็น user จริง** → D2.4 (fallback ไปแพลตฟอร์ม) จะทำงานจริงกับผู้ใช้แค่ **13 คน**
- แต่ **1,548 คน (47%) มี `suggester_code = 99999999` อยู่แล้ว** คือแพลตฟอร์มเป็นผู้แนะนำเอง → แพลตฟอร์มได้ทั้ง 30 + 20 = **50 pp/ครั้ง** สำหรับกลุ่มนี้
- **ไม่มี self-referral เลย** (0 คนที่ `suggester_code = personal_code` ของตัวเอง) — ช่องฟาร์มแบบแนะนำตัวเองยังไม่ถูกใช้ แต่ควรใส่ guard กันไว้
- **มาร์จิ้นแท้จริงสูงกว่าตัวเลขบนกระดาษ**: ถ่วงน้ำหนักด้วยสัดส่วน 47% → แพลตฟอร์มได้เฉลี่ย ~34 pp/ครั้ง → **~21.3% ต่อ 1 บาทบริจาค** (ไม่ใช่ 16.7%)
